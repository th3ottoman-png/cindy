dev sandbox `CindyGlobal-dev2-dev`) and **failed to call the tool**. Hermes answered that no `cindy_docs` tool was available.

## Root cause (diagnosed, not yet re-proven by a clean run)

Hermes expands `${CINDY_BRIDGE_SESSION}` in the MCP `env:` block from the **gateway process environment** at connect/reconcile
time, not from the per-session `query/start` env. The gateway in use was a leftover from my own 4a harness run:

```
12104 Thu Oct 29 18:37:19 2026     /Users/turko/.hermes/tools/python-3.14.9+20261021-darwin-arm64/bin/python3 -m hermes_cli.main --profile d
CINDY_BRIDGE_SESSION=live-1b4
```

So the shim asked for session `live-1b4` (4a) instead of the app's session. This contaminated the run, but it also exposes a real
design risk: one gateway serves many Cindy sessions, and its MCP children are connected once with the gateway's env, so a
per-session env var in `config.yaml` cannot carry per-session identity even in a clean run. The 1.5b-1 probe used `hermes mcp test`,
which expands from its own process env and so could not show this.

## Other miss

The prompt used a relative CSV name placed in the sandbox's default bot workspace, but the Hermes session ran in
`.../dialogues/2026-10-29/<session-id>/`. `read_sheet` is bound to the session working directory, so even with tools connected the
file would not have been found. A retry must put the file in the session's actual directory.


## Free control experiment (no model call), same day

Throwaway `HERMES_HOME`, Hermes v0.22.5, stub stdio MCP server that records the `CINDY_PROBE` value it receives; config entries use
`CINDY_PROBE: "${CINDY_PROBE}"` exactly like the shim entry.

1. Gateway started with `CINDY_PROBE=gateway-val` (`hermes gateway ensure`). Entry `envprobe1`, present at start, recorded
   `{"probe":"gateway-val"}`.
2. While the gateway ran, entry `envprobe2` was appended to `config.yaml` by a **different process** (shell with a different env). Hermes
   reconciled it on its own about 60 s later (no client, no trigger) and the child recorded `{"probe":"gateway-val"}`.

```
2026-10-29 18:45:00,461 INFO tools.mcp_tool: MCP server 'envprobe1' (stdio): registered 1 tool(s): mcp__envprobe1__ping_cindy
2026-10-29 18:46:01,078 INFO tools.mcp_tool: MCP server 'envprobe2' (stdio): registered 1 tool(s): mcp__envprobe2__ping_cindy
2026-10-29 18:46:01,078 INFO gateway.run_profile_reconcile: MCP servers reconciled with config (default): removed=[] added=['envprobe2']
```

Result: `${VAR}` in an MCP `env:` block is expanded from the **gateway process environment**, whoever wrote the config. Combined with
`hermes-run.ts` (each Cindy turn spawns a `hermes chat` client with the per-session env, and "`hermes chat` always launches through
Hermes's canonical gateway"), per-session env cannot reach MCP children when one gateway serves the sessions. The failed 4b run is the
live confirmation: the client env held the app's session id, the shim received the gateway's `live-1b4`.

Hermes offers no per-run MCP flag (`hermes chat` has `-t/--toolsets` only; `hermes mcp` manages config). It does key gateways per
profile/home (`--profile`, `profile_id` = home path).


## Option (a) probe: one gateway per Cindy session via a per-session `HERMES_HOME` (free, same day)

Throwaway homes in the scratchpad, Hermes v0.22.5, the stub env-recording MCP server, `hermes gateway ensure` as the stand-in for the
gateway start that `hermes chat` triggers (a real `hermes chat` needs a model call, so the client-triggered start was NOT exercised).

| Home | Gateway env `CINDY_PROBE` | MCP child saw | Time to ready |
|---|---|---|---|
| A (own config) | sessA | sessA | 14.34 s (cold) |
| B (own config) | sessB | sessB | 9.11 s (cold) |
| C (config.yaml = symlink to one shared file, `DUMP_OUT`/`CINDY_PROBE` via `${VAR}`) | sessC | sessC | 14.02 s (cold) |
| D (same shared file) | sessD | sessD | 8.69 s (cold) |
| A again, `CINDY_PROBE=other` | (already running) | unchanged `sessA` | 0.38 s (warm) |

Findings: gateways are keyed by home, so four homes gave four independent gateways, each MCP child receiving its own gateway's env. A
symlinked shared `config.yaml` is followed. A warm re-ensure ignores the new env (a gateway keeps the env it started with). Cost: a cold
home takes 9–14 s (Hermes prepares its Python runtime per data root), and each gateway holds about 250 MB RSS. Each home also gets its own
skeleton (`sessions`, `memories`, `skills`, `plugins`, `state.db`, `kanban.db`, `auth.lock`, ...), which a per-session home would fragment.
