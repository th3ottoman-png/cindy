# 13.7 — Chat width preference (live proof)

- **Date:** 2026-11-14
- **Row:** ROADMAP 13.7. Blueprint §9.
- **Environment:** Node v22.23.4, dev app `CindyGlobal-dev2-dev` from the canonical wrapper
  (`DESKTOP_DEV_VERDICT=ready`, pid 86813, CDP 9222).
- **Cost:** no model turn, no API call, no new outbound request.

## What shipped

- `chatWidth: 'regular' | 'wide' | 'full'` (default `regular`) in the same
  `cindy.responsePreferences.v1` store; an unknown value falls back to `regular`.
- `chatMaxWidth(width)` → 914 / 1200 / `Infinity`. `Infinity` is how `useProportionalWidth`
  expresses "no cap": it clamps to the measured container, so `full` fills the available width
  with the hook's existing proportional padding intact.
- The literal `914` is gone from both `useProportionalWidth` call sites
  (`CCAgentSessionView.tsx`, `NewMakerDraftRoute.tsx`); both read the same preference, so the
  composer does not jump on first send.
- **Card sweep:** 11 hard-coded `max-w-[914px]` caps across 10 components became
  `max-w-[var(--cindy-message-width,914px)]` — the variable the hook already publishes on the
  column container. Same value by default, and cards now follow the column instead of staying
  narrower than it in wide/full mode. Outside the column the 914 px fallback applies, so dialogs
  are unchanged. Components: InputHandoffCard, RemoteDesktopConfirmationNotice, IssueConfirmCard,
  RenameSessionsConfirmCard, GhostGrantConfirmCard, DecisionCards, PlanActionCard, PermissionPrompt,
  PlanViewerCard (×2), InteractionPromptSlot.
- Settings → Personalization → Response style: a "Chat width" select (English only, no new keys).

## Live proof — real window at 1600 px

Driven through the real Settings select, reading the hook's own CSS variables:

```
regular  messageWidth 914px   inputWidth 934px   innerWidth 1600  hScroll false
wide     messageWidth 1200px  inputWidth 1220px  innerWidth 1600  hScroll false
full     messageWidth 1240px  inputWidth 1260px  innerWidth 1600  hScroll false
regular  messageWidth 914px   inputWidth 934px   (restored)
```

`full` = 1240 px rather than 1600 because the content container is 1340 px after the rails, minus
the hook's 50 px message padding each side. That is "no cap, fill the container", exactly as the
blueprint specifies. **No horizontal scroll in any mode** (`scrollWidth === clientWidth`).

## Live proof — compact rail unchanged

Viewport narrowed to 760 px (container 500 px) under both preferences:

```
fullWide       innerWidth 1440  container 1180  messageWidth 1080px  compact false  hScroll false
fullNarrow     innerWidth  760  container  500  messageWidth  460px  compact true   hScroll false
regularWide    innerWidth 1440  container 1180  messageWidth  914px  compact false  hScroll false
regularNarrow  innerWidth  760  container  500  messageWidth  460px  compact true   hScroll false
```

The compact rail engages at the same threshold and produces the **identical** 460/480 px layout
under `full` and `regular`. The preference only changes the cap, never the compact logic.

**Measurement note:** the first narrow reading was stale (3 s wait after a viewport override, with
the preference changed via localStorage + reload). Re-measured with the real Settings select and an
8 s settle, the container genuinely shrinks to 500 px and `compact` flips true. A real OS window
resize was not possible — `osascript` lacks assistive access on this machine — so the narrow case
uses CDP viewport emulation, which does drive the same ResizeObserver path.
