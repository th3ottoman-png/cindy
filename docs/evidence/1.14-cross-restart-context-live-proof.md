# 1.14 — Agent context survives an app restart (live proof)

**Date:** 2026-11-14 · **Build:** dev sandbox `CindyGlobal-dev2-dev`, CDP 9222 · **Hermes:** 0.23.0
**Model:** `qwen3-8b` on LM Studio (local, **zero API spend**) · **Conversation:** `ef62593b-1c5f-49f1-ae32-dd25180d3b58`

## The defect

`HermesAgent.startSession` minted `const sessionId = randomUUID()` on every start. That id names the
per-session home (`session-homes/<id>-<sha256[0:10]>`), so every app restart produced a **new home with an
empty `state.db`**, while `resumeHermesSessionId` still carried the persisted `sdk_session_id`.
`hermes chat --resume <id>` could not resolve it there, `isInvalidResumeFailure` fired, and the daemon
replayed the input against a fresh session (`resume-reset`). The owner's visible transcript was never lost
(Cindy's own SQLite); the **agent** forgot everything on every restart. Same mechanism behind orphan-home
accumulation.

## The fix

1. `packages/maker-core/src/agents/hermes/daemon-session-id.ts` — `hermesDaemonSessionId(cindySessionId)`
   derives a stable, namespaced id (`cindy-<cindySessionId>`, sanitised). No Cindy id → a random UUID,
   so throwaway worker runs are unchanged.
2. `agent.ts` uses it instead of `randomUUID()`.
3. `hermes-manager.ts` `query/start` is now **idempotent**: an existing record is adopted (start fields
   re-applied, `hermesSessionId` / `launch` / `lastSeq` preserved) instead of raising
   `SESSION_ALREADY_EXISTS`. A live turn still owns the session exclusively. An explicitly cleared binding
   (`''`) stays cleared, so a deliberate fresh start is not resurrected.

The `resume-reset` fallback is untouched: an unresolvable id still replays fresh and the turn still answers.

Objective corroboration, independent of what the model said:

- The home's own `state.db` keeps **one** session row with the **same id** across both restarts, and its
  `message_count` grows 5 → 7 → 9. A reset would have created a second session row.
- The recall question was chosen so the answer exists **only in the conversation**: the upgrade turn had
  also written `STABLE_114` into the agent's `memory` tool, so a token-only question could have been
  answered from memory. Quoting the previous instruction verbatim cannot.
- Home count stayed **170** across both restarts — no new home per start, which is the orphan-accumulation
  mechanism removed.
- Stable home name is exactly the predicted `cindy-ef62593b-1c5f-49f1-ae32-dd25180d3b58-93b94cb4d9`.

## Measured limit: a pre-1.14 conversation resets exactly once more

The upgrade turn (20:33) still reported one `resume-reset`. That is expected and unavoidable without
mutating the agent's transcript database: the conversation's context lives in a home named after a legacy
per-start UUID, and the new stable id names a different home. From that turn on, context survives every
restart. New conversations are stable from their first turn.

### Why the obvious migration (rename the legacy home) was tried and removed

A first implementation adopted the legacy home by renaming it to the stable path, so existing
conversations would keep their context with no extra reset. Unit tests passed (the fake CLI keys sessions
by id only). **Live, it broke the turn**:

```
role  | content                                              | time
user  | What token did I ask you to remember? …              | 2026-11-14 20:18:11
error | {"message":"profile_mismatch","providerId":"lmstudio-local"} | 2026-11-14 20:18:11
```

Traced into the installed CLI:

- `hermes_cli/gateway_connection.py`: `RESUME_GONE = RESUME_REFUSALS | {"profile_mismatch"}` —
  *"raised for another profile's session"*.
- `hermes_cli/gateway_runtime_service_identity.py` `verify_home()` raises `profile_mismatch` when the
  running home and the recorded one differ.
- The home's `state.db` records `profile_id` / `home` as the **absolute home path** (probe: 8–43
  occurrences per DB), and `gateway_state.json` publishes `hermes_home`.

So a session is bound to a profile identity derived from its home path. Renaming the home makes the
session belong to *another profile*: `--resume` is refused and the turn **errors** instead of resetting —
strictly worse than no migration. Clearing the runtime identity files (`gateway_state.json`, `gateway.lock`,
… the same set Hermes's own home import skips, `_IMPORT_SKIP_NAMES` in `hermes_cli/backup.py`) did **not**
fix it, because the binding also lives inside `state.db`. The rename migration and its helper were removed;
the home used in the experiment was renamed back to its original legacy path and its gateway stopped.

Adopting legacy context would require either rewriting profile identity inside the agent's `state.db`
(rejected: mutating the transcript store) or a persisted per-record home override so the path never changes
(possible future work, recorded in §Debt).

## Compatibility with 13.2c housekeeping (checked, not assumed)

`scanStorage` builds `owners = new Set(registry.map((r) => r.sessionId))` and derives a home's owner from
`HOME_NAME = /^(.+)-[0-9a-f]{10}$/`. The new home's prefix **is** the stable registry id
(`cindy-ef62593b-1c5f-49f1-ae32-dd25180d3b58`), so the home is recognised as **owned**, not orphaned, and
`statusOf(owner)` still resolves the conversation through the registry's `hermesSessionId` → Cindy
`sdk_session_id` join. The name also stays under `sessionHomePath`'s 48-character truncation
(`cindy-` + a 36-char UUID = 42), which is why the live home name matched the predicted name exactly.
No housekeeping change was needed.
