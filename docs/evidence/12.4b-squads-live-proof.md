   collect the three answers and summarize in one line." → Open lead task. Navigates to

## Bug found by the proof, fixed in the same commit

**The new-draft first send consumed `@agent:` tokens as 8.4 turn attachments.** The first launch
(lead `bccf0a65`) produced **0** `teammate mention dispatched` entries: the lead's stored first message
was an 8.4 preamble (`[Attached for this turn only: agent "expert:code-reviewer" …]`), and the
orchestrator lead — whose prompt drives orchestration — salvaged it by starting its own Orca team
(`cindy_orca.start_team`) instead of the 12.3 registry join. That only worked because the lead happened
to be the orchestrator; a plain lead would not have joined anyone.

Root cause (two spots):
- `NewMakerDraftRoute.tsx` applied `applyTurnAttachments(..., { preserveKinds: ['skill'] })`, so
  `@agent:` tokens were stripped before the host send boundary saw them. (The running-session composer
  does not apply 8.4 in the renderer, which is why 12.3a/b worked there.)
- `TurnAttachmentSlot.tsx` resolved every `@kind:id` token into an attachment item, including the
  non-attachable `agent` kind, so the tokens also became chips/preamble.

Fix (both minimal, aligned with the 12.3 design that `agent` is not an attachable kind):
- `TurnAttachmentSlot` filters `agent` tokens out of the resolved attachment items.
- `NewMakerDraftRoute` preserves `['skill', 'agent']` so the tokens survive to the host boundary.
- Regression: `TurnAttachmentSlot.test.tsx` "leaves @agent: teammate tokens unattached for the send
  boundary" (no chip, nothing published, token stays in the draft). 21 slot tests green.

Re-running the launch after the fix joined all three members through the 12.3 registry (step 4). Normal
8.4 turns are unchanged: the 20 pre-existing slot tests and the draft-submission suite stay green (no
`agent` token → nothing filtered or preserved).

## Honest limitations

- **Lead synthesis under local-model contention.** With four Hermes sessions sharing one local Gemma
  endpoint, the lead's collect-and-summarize turn collided with arriving worker reports
  (`[TURN_ALREADY_RUNNING]`), and one worker misreported a binding error ("Expert Orchestrator … set to
  hermes, but this session is running on claude-code"). The DB disproves it: lead and all three workers
  are `agent_kind=hermes`, `hermes-default`, Full access. A follow-up nudge produced a lead reply, but
  the local model's synthesis was degraded. This is the same local-model turn contention recorded in
  12.3b, not a squad defect: the join, dispatch, per-member completion and visibility are all proven.
- **`max_turns` is stored, validated and carried in the plan, but the live worker turn cap is the
  proven 3.9 default (40).** Threading a custom per-squad cap through worker creation is a hot-path
  change deferred to a follow-up; the done-when does not depend on it.
