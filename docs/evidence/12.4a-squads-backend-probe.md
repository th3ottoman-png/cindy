# 12.4a probe — are upstream bot groups local in this fork?

**Date:** 2026-11-14, dev app `CindyGlobal-dev2-dev` (region global), Node 22.23.4, macOS 27.2.
**Mode:** local (`app-session.json` `activeMode: "local"`), **no Cindy account**. Network off via a
macOS Seatbelt profile applied to the whole dev process tree. **No feature code was written.**
Decision: ADR `0012-squads-backend.md` (squads launch Orca teams, not bot groups).

## 1. Method — network off for the app process tree

The dev app was launched inside `sandbox-exec` with a Seatbelt profile that denies outbound
networking except loopback and unix sockets, so the local model endpoint (LM Studio,
`127.0.0.1:1234`), the Hermes daemon socket and CDP keep working while anything outbound fails:

```
(version 1)
(allow default)
(deny network-outbound)
(allow network-outbound (remote unix-socket))
(allow network-outbound (remote ip "localhost:*"))
```

Launch: `sandbox-exec -f no-outbound.sb script -q <log> node scripts/desktop-dev-runner.mjs remote`
with the restart script's sandbox env (`CINDY_AUTH_REGION=global XDT_ISOLATED=1 XDT_ISOLATED_NAME=dev
XDT_USER_DATA_DIR=…/CindyGlobal-dev2-dev XDT_USER_DATA_DIR_EPOCH=1 ELECTRON_DISABLE_SANDBOX=1
ELECTRON_EXTRA_LAUNCH_ARGS=--no-sandbox`), opened through Terminal.app. `ELECTRON_DISABLE_SANDBOX`
is required because Chromium's own child-process sandbox cannot initialize inside the outer
Seatbelt profile (`sandbox initialization failed: Operation not permitted`); the outer profile still
confines the whole tree.

**Profile verification (before trusting it):** under the profile, `curl https://1.1.1.1` and
`curl https://chatgpt.com` fail to connect (EPERM), while `curl http://127.0.0.1:1234/v1/models`
returns 200. The app's own startup confirms denial from inside the tree:

```
[provider-service] remote catalog read/parse failed, trying fallback
   url: 'https://model-access.cindy.app/api/model-catalog/catalog'
   err: 'Error: net::ERR_ACCESS_DENIED'
[provider-service] loaded last-known-good catalog snapshot
[voice-input:refine-model] codex responses prewarm failed (non-fatal) { error: 'fetch failed <- EPERM' }
[serverApiClient] serverApiFetch.redacted_not_ok path=/api/plugins method=GET status=0 code=NETWORK_ERROR
```

`lsof` on the Electron main process showed **no external TCP connection** during the offline run.

### 1.1 Honest caveat — a first, misconfigured profile let traffic out

The first profile draft also contained `(allow network-outbound (local ip "localhost:*"))`. That
rule inadvertently allowed **all** outbound (a `local ip` filter matches the local endpoint of every
outbound socket). Under it the app reached the network: it loaded the catalog **from remote**
(`loaded catalog from remote`, 01:45:31) and logged Codex endpoint prewarms (`status 200`) and
prompt-prediction turns "generated on routed endpoint", and a Codex turn was registered for a newly
created probe bot. This was detected (an established external TLS connection in `lsof`; catalog
loaded from remote), the offending rule was removed, the profile re-verified to block external, and
**the entire probe was re-run offline**. All decisive evidence below (group `AUTH_REQUIRED`, offline
message failure) was captured in the corrected offline run. The misconfigured window caused a small
number of unintended Codex requests against the owner's subscription; no probe result relies on them.

Seatbelt notes learned the hard way (recorded so the next probe does not repeat them):
- `(remote ip "<host>:<port>")` accepts only `*` or `localhost` as host — `127.0.0.1:*` / `::1:*`
  are rejected at profile compile (`host must be * or localhost in network address`).
- A `local ip` allow rule is a hole for outbound; do not use it to "allow loopback".
- `/bin/ps` cannot be exec'd inside the profile (kernel-restricted), so the restart script's
  process-table scan fails under Seatbelt (`PROCESS_SCAN_FAILED … spawnSync ps EPERM`). The probe
  therefore ran `desktop-dev-runner.mjs` directly (no scan needed; the app was already stopped).

## 2. Creating bots (works offline)

Two local bots were created through the UI (Teammates → Create → New teammate): **Probe Alpha**
(`bot_1794620813224_1g8i9v`) and **Probe Beta** (`bot_1794620847098_iwkq7c`). Creation is local
(profile + canonical session + workspace under `owners/<owner>/bots/<id>/workspace`). The creation
dialog's default model read **Codex · GPT-6-Luna · Medium** ("Follows the default teammate model").
Screenshots: `/tmp/proofs/12.4a/02-new-teammate-dialog.png`, `03-after-create-alpha.png`.

Bot harness is `cc | codex | pi` only (`botSessionAgentKind`, `localDb/ipc/bots.ts:887`); Hermes is
filtered out of the bot default chain. The provider catalog does include a local LM Studio provider
(`cindy-local-lmstudio`, agents cc/codex/pi, routing to `http://127.0.0.1:1234`), so member turns can
be pointed at local models — but that does not affect group creation.

## 3. Creating a bot group — refused offline (and it is an auth gate, not a network gate)

Teammates → Create → New Group Chat → name "Probe Squad", select Probe Alpha + Probe Beta
(2 selected) → Create Group Chat. Result:

> Your sign-in has expired. Sign in again on your computer.

Main log (offline run): `[2026-11-14T01:58:36.660] [WARN] [maker-ipc] Chat group action failed { code: 'AUTH_REQUIRED' }`.
`chatServer.status()` returned `{ enabled: true, connected: false }`; `chatServer.ownedBots()`
returned `{ ok: false, errorCode: 'AUTH_REQUIRED' }`. Screenshot:
`/tmp/proofs/12.4a/11-offline-group-create.png`.

This is **structural**: `withChatServer` (`chatServer.ts:284`) routes `createGroup` to the cloud API
(`createChatServer.createGroup` POSTs `/conversations`, `chatServer.ts:2760`), and `api()` rejects
`AUTH_REQUIRED` when there is no access token (`chatServer.ts:562-568`) — before any HTTP request.
The local `createGroup` (`botGroupChatService.ts:1818`) is never reached; `local.*` is used only for
one-way migration of old local groups to server rooms (`chatServer.ts:706`), lane settlement, and
companion task messages. The identical refusal was reproduced with the network on, confirming it is
an account gate independent of connectivity.

## 4. Sending one message — the member turn needs the cloud by default

With no group creatable, the member-turn runtime was probed through a bot's own chat (the same
`dispatchBotSessionMessage` path a group lane uses, `register.ts:12920`). In Probe Alpha's chat,
sent: "Reply with the single word OK." (01:59:20). The Codex turn dispatched and failed offline:

- UI: "Network error: the service is temporarily unreachable. Click \"Retry\" to try again."
- Error details: `unexpected status 502 Bad Gateway: upstream unreachable: AggregateError,
  url: http://127.0.0.1:59324/responses`.
- Agent log: `codex-proxy … upstream request failed … err: AggregateError … path:
  /backend-api/codex/responses` (64 such entries; upstream base `https://chatgpt.com/backend-api/codex`).
- Codex stderr: `ERROR codex_api::endpoint::responses_websocket: failed to connect to websocket:
  HTTP error: 502 Bad Gateway, url: ws://127.0.0.1:59324/responses`.

Screenshots: `/tmp/proofs/12.4a/12-offline-message-sent.png`, `13-offline-turn-result.png`,
`14-offline-error-details.png`.

## 6. Conclusion

Bot groups are **not local** in this fork: the group lifecycle (create/send/continue/stop/plans) is
routed through the cloud Chat Server API and requires a Cindy account, which local mode does not
have. Orchestration storage is local and member turns can target local models, but neither unlocks
group creation. Per blueprint §5, squads (12.4b) therefore launch **Orca teams** (Hermes lead +
workers), the backend already proven local in 12.3. See ADR 0012.
