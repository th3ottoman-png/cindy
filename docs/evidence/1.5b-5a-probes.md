# 1.5b-5a — free probes for gateway-per-session (2026-10-29)

Hermes Agent v0.22.5. Throwaway homes in the session scratchpad, stub stdio MCP server that records the `CINDY_PROBE` it receives, scrubbed
environment (`env -i`, no API keys), no credentials anywhere, so no model call could be made (a real `hermes chat` stopped with "No usable
credentials found for provider 'deepseek'", 0 tokens). Nothing under `~/.hermes` or `~/.hermes-cindy` was read for these probes except
`ls`/`du` of the Cindy home for sizes; the real `config.yaml` is byte-identical to its backup afterwards. All probe gateways stopped, scratch deleted.

## Q1. Does a real `hermes chat` client start the gateway with its own env?  **Yes.**

`echo hello | env -i ... CINDY_PROBE=clientval hermes chat --format stream-json --query-file - --in <dir> -m deepseek-flash --provider deepseek`
on a home with no gateway: the client started one; `ps eww` showed `CINDY_PROBE=clientval` and the home in the gateway's env; the MCP child recorded
`clientval`. A second client with a second home started a second gateway with `client2`. So with one home per Cindy session, the per-session env set
on the `hermes chat` spawn (as `hermes-run.ts` already does) reaches MCP children, provided the gateway for that home is not already running.

## Blocker found on the way: `--safe-mode` disables MCP servers

`hermes chat --help`: "`--safe-mode` Troubleshooting mode: disable ALL customizations — user config, AGENTS.md/memory injection, plugins, and MCP servers
(implies --ignore-user-config and --ignore-rules)". `permissionModeToFlags` in `hermes-run.ts` passes `--safe-mode` for every Cindy permission mode except
`bypassPermissions` (which passes `--yolo`, "bypass all dangerous command approval prompts"). So a "Default permissions" Hermes session in Cindy runs with
MCP servers off, independent of the identity problem. This is consistent with the failed 4b run (Hermes listed only `terminal` and `todo`). Not isolated by a
test (listing a run's tools needs a model call). `--safe-mode` also needs an explicit `-m`, which Cindy already passes.

## Q2. What does Hermes write into a home; do shared symlinks survive?

- Symlinks to `.env`, `auth.json`, `SOUL.md` and to the dirs `skills`, `plugins`, `memories` all stayed symlinks after a client + gateway start; the three plain
  files kept their hashes. Hermes seeded 656 bundled skill files into the shared `skills` dir (first run into an empty dir), so share `skills` from a pre-seeded dir.
- Hermes' own `hermes config set` on a symlinked `config.yaml` writes **through** the link (target updated, link kept). Cindy's `hermes-config.ts` writer uses
  temp-file-plus-rename, which would replace a link, so the per-session `config.yaml` must be a **generated regular file**, not a link to shared config.
- Per-home state Hermes creates itself: `state.db`, `kanban.db`, `projects.db`, `sessions`, `logs`, `gateway.*`, `spawn-ledger.json`, `install_id`, `auth.lock`.
- Sessions are per home: two homes each listed only their own session.
- Not tested (needs credentials or a model call): an OAuth/`auth.json` refresh write-back from a session home. If Hermes rewrites `auth.json` by rename, a
  symlinked `auth.json` would be replaced and refreshed tokens would not reach the shared copy.

## Q3. What must be shared?

Share by symlink (read-mostly): `.env`, `auth.json` (see caveat), `SOUL.md`, `skills`, `plugins`, `installs`. Per session: `config.yaml` (generated), `state.db`,
`sessions`, `kanban.db`, `projects.db`, logs, gateway files. `memories` is a product decision: shared = one memory across sessions, per-session = isolated.
Cindy's existing history in `~/.hermes-cindy` (`state.db`, sessions) would not be visible in a new per-session home; resume only works inside the same home.

## Q4. Can a template home hide the 9–18 s cold start?

- Copying a warmed home as a template **fails**: "dependency environment is missing or outside this install" — the venv under `installs/<id>/environments/<id>/venv`
  is recorded by absolute path of the original home. (My first timing of 0.76 s was a fast failure, exit 1, not a start; caught because only 2 of 3 gateways were up.)
- Sharing the warm `installs/` directory by symlink **works**: gateway up with the right per-home env.

| Home | Time to gateway ready | Disk |
|---|---|---|
| fresh, no sharing | 17.97 s, 11.18 s | 1.0 GB (`installs` 597 MB + `cache` 446 MB) |
| symlinked shared `installs/` | 7.24 s, 6.80 s, 1.79 s | 5 MB |

So per-session homes should share `installs/` (and probably `cache`), costing about 5 MB each and ~2–7 s to start; starting the gateway when the Cindy session
is created (before the first turn) can hide most of that. About 250 MB RSS per gateway still applies (earlier probe).
