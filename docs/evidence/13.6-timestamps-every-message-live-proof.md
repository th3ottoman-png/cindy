# 13.6 extension — timestamps on every message: live proof

- **Date:** 2026-11-14
- **Row:** ROADMAP 13.6 (extension asked for by the owner: "yes" to covering every message,
  not only where `MessageActionBar` mounts)
- **Label:** `live-proven`
- **Cost:** none. No model turn, no API call, no file outside the renderer.

## The gap that was closed

`MessageStream.tsx` mounts the action bar only on a turn's final body:

```tsx
// turn 结束后只有收尾正文出现 —— 中间句彻底不挂 bar。
showActionBar={Boolean(assistantIsTurnFinal) && !assistantForkBlocked}
```

So intermediate assistant messages had no bar and therefore no clock, even with
`showTimestamps` on. The 13.6 proof recorded this as a limitation; the owner asked for it removed.

## Change

- Extracted the shared time element into `TimeText` and added an exported **`MessageClock`**
  in `MessageActionBar.tsx`. It reads `useResponsePreferences()` itself, returns `null` when the
  preference is off or the timestamp is unusable, and never depends on hover or on the bar's fade.
  `MessageActionBar` now renders `<MessageClock>` instead of its own inline clock, so there is one
  clock implementation, not two.
- `AssistantMessage.tsx` renders `<MessageClock>` below the bubble when there is **no** action bar,
  the message is not streaming, and the preference is on. It sits outside `Collapse` (which is
  closed for these messages) and outside the fade.
- No change to the action bar's own behaviour, to the relative hover text, or to the transcript.

## Live measurement (real Settings checkbox, real session)

Session `5be0ad2a-61d4-41af-9576-941039e6d1f9`, which has four assistant messages from Nov 12
plus later turns. Counted `<time>` elements whose text is a clock (`HH:MM` or `MMM D, HH:MM`),
alongside the number of action bars (Copy buttons):

| Preference | Clocks | Action bars | Clock texts |
|---|---|---|---|
| **on** | **10** | 8 | `Nov 12, 07:57`, `Nov 12, 08:01`, `Nov 12, 08:03`, `Nov 12, 08:04`, `12:07` ×3, `17:24` ×3 |
| **off** | **0** | 8 | — (hover-only relative text restored) |
| **on, after a full page reload** | **10** | 8 | identical list |

**10 clocks against 8 action bars** is the proof: two messages that mount no bar now carry a
clock. Before the extension the same session showed 8. The Nov 12 group is the clearest case —
previously only `07:57` (the turn's final body) was visible; now `08:01`, `08:03` and `08:04`
(the intermediate chunks) are too.

Total `<time>` count went 42 (on) → 40 (off): the two standalone clocks disappear and the eight
bars swap their clock back to relative text, which accounts for the difference exactly.

Toggling was done through the real **"Always show message timestamps"** checkbox in
Settings → Personalization → Response style, not by writing localStorage. The reload was
`location.reload()` on the session route.

## Tests

fade and the right `datetime`, unusable timestamp → nothing, right-alignment spacing kept).
The 27 existing assertions — including the three 13.6 bar tests — pass unchanged after the

## Scope note

This covers user messages and **all** assistant messages, including intermediate chunks. Tool
call cards and work-group headers are not messages and carry no `createdAt` of their own; they
are unchanged. System cards are unchanged.
