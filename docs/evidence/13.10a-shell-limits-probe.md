## F1 — Which `terminal:` settings exist

`TERMINAL_CONFIG_ENV_MAP` (`hermes_cli/config.py:2014-2026`) is the authoritative list of
config keys under `terminal:`: `backend`, `modal_mode`, `degraded_mode`, `cwd`, `temp_dir`,
**`timeout`**, `lifetime_seconds`, `docker_image`, `docker_forward_env`, `modal_image`,

`ssh_key`, `container_cpu`, `container_memory`, `container_disk`, `container_persistent`,

`docker_persist_across_processes`, `docker_shared_container_key`, `docker_orphan_reaper`,
`sandbox_dir`, `persistent_shell`.

**There is no output/character cap key.** No `max_output_chars`, no `max_output`, nothing of
that shape, in the config map, in `hermes_cli/config_defaults.py`, or in
`cli-config.yaml.example`.

## F2 — `terminal.timeout`

- Integer seconds. **Default 180.** Proved two ways: a brand-new home reports
  `hermes config get terminal.timeout` → `180`, and the code fallback is
  `_parse_env_var("TERMINAL_TIMEOUT", "180")` (`tools/terminal_tool.py:854`);
  `cli-config.yaml.example:442` ships `timeout: 180`.
- Foreground hard cap **600 s**, env `TERMINAL_MAX_FOREGROUND_TIMEOUT`
  (`FOREGROUND_MAX_TIMEOUT`, `tools/terminal_tool.py:77`). A requested timeout above the cap is
  not refused: the command is promoted to a background job with a note
  (`tools/terminal_tool.py:1244-1265`).
- `terminal.persistent_shell` also exists, default true; the local backend reads
  `TERMINAL_LOCAL_PERSISTENT` (`tools/terminal_tool.py:862-864`).

## F3 — What the model sees at the limit

The literal marker **`[Command timed out after Ns]`** plus **exit code 124**
(`tools/environments/base.py:770` renders the suffix;
`tools/file_operations_search.py:676` the search variant). Observed verbatim three times:

| probe | config | marker |
|---|---|---|
| `timeout-probe.log` | `timeout: 5` | `[Command timed out after 5s]` |
| `gwA.log` | `timeout: 8` | `[Command timed out after 8s]` |
| `t1.log` / `t2.log` | per-call `timeout=30` | `[Command timed out after 30s]` |

No partial-output marker and no truncation notice accompany a timeout: the model gets the
marker and the exit code, and nothing else about the interrupted command.

## F4 — A per-call `timeout=` beats the config

Same three probes. With the config at 5 s, a call that passed `timeout=30` ran for 30 s. This
matters for 13.10b: a session-home limit is a **default**, not a ceiling, unless something also
stops the model passing its own value.

## F5 — There is no configurable output cap; the real cap is the context budget

What exists instead is the generic tool-result budget
(`tools/budget_config.py`):

- per-result threshold = `min(registry max_result_size_chars, default_result_size)`
  (`resolve_threshold`, `tools/budget_config.py:66-80`);
- `default_result_size` = **15 % of the model's context window in characters**, floored at
  8,000 and capped at 100,000 (`budget_for_context_window`, `tools/budget_config.py:96-113`);
- the terminal tool registers `max_result_size_chars=100_000`
  (`tools/terminal_tool.py:1757`), so on a 200K+ model the cap is 100,000 characters;
- per-turn aggregate 200,000 characters; preview 1,500 characters
  (`tools/budget_config.py:14-16`);
- the **only** config key that moves any of this is `tool_budget.mcp_result_size_chars`
  (`tools/budget_config.py:26-41`), and it applies to `mcp_` tools only.

Consequence, observed: the probe home ran a small-context local model, so its effective cap sat
far below 100,000, and a **59,495-character** result spilled (`output-probe.log`).

## F6 — Over the cap the result is persisted, not truncated

`maybe_persist_tool_result` (`tools/tool_result_storage.py:395-424`) replaces the result with a
`<persisted-output>` block: a ≤1,500-character preview, a `...` if there is more, and
`Full output saved to: <path>`. Canonical home is always
**`$HERMES_HOME/cache/spillover/<id>.txt`** (`tools/tool_result_storage.py:1-8`, `:26`).
Observed: `home/cache/spillover/911991588.txt`, 59,495 bytes, and the model read it back with
`read_file`. The model reported **no truncation marker** — because there is none.

## F7 — A session-home config change needs no gateway restart

The terminal policy is rebuilt **per routed turn/poll** from the profile's `config.yaml`,
signature-cached on the file (`tools/terminal_scope.py:120-190`; the comment at the read site
says exactly that). A long-lived gateway therefore sees a hand edit on the next command.

Observed: the gateway started once (`home/gateway-starts.log` holds a single timestamp
`1794733680.637515`; pid 31147 was still running at 09:27, ~19 minutes and four probes later),
the config went 5 → 8, and the next command reported `[Command timed out after 8s]`.

## What this means for 13.10b

The row as written wants `shell-limits.yaml` with `timeout_seconds` and `max_output_chars`,
written into each session home's config, "only settings 13.10a proved exist". The probe splits
that in two:

- **`timeout_seconds` is real and writable.** `terminal.timeout` exists, defaults to 180, and is
  honoured per call. Two limits on it: the 600 s foreground cap, and F4 — a per-call `timeout=`
  overrides it, so it is a default, not a ceiling.
- **`max_output_chars` has nothing to write to.** There is no output-cap setting in Hermes
  0.23.0. The built-in behaviour is the context-scaled budget in F5 and the spill-to-file in F6.
  A Cindy-side cap therefore has to be enforced where Cindy receives the tool result (host
  side), not by a config key in the session home.

13.10b must be re-scoped on that basis before any code is written. Recorded in ROADMAP 13.10b
and STATUS 2026-11-15 (av).
