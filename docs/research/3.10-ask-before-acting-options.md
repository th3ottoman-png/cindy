# ROADMAP 3.10 "Ask before acting": problem, findings, options

Status: **decided 2026-11-03, see `docs/decisions/0009-hermes-options-first-chat.md` (A now, D next, read-only facades).** Originally Written 2026-11-03 to get a second opinion before the owner picks.
Nothing is built. This file is self-contained: a reviewer does not need the repo to follow it.

---

## 1. The problem (as first written on the ROADMAP)

> **3.10 Ask before acting.** When the owner asks for options or suggestions, the agent lists them and
> stops; it starts nothing (no file writes, no runs beyond reading) until the owner picks.

**The incident (2026-11-02):** in the chat "Suggest Tasks to Save Time" (Chat `885ab7a2`, Hermes agent,
model route `hermes-default`, access level **Full access**), the owner asked the agent to suggest tasks
and let the owner choose. Instead, the agent started building a CSV normalizer on its own.

**Acceptance test (from the ROADMAP):** in a Hermes session on Full access, the owner asks for options.
The agent lists them and waits. No file changes happen until the owner picks.

**Design options listed at the start:**
1. A lower access level.
2. A rule in the Hermes home, written by the owner.
3. A built-in mode.

**Hard rule:** existing agents' system prompts must not be edited (see §4).

---

## 2. What Cindy is (enough context to judge the options)

- Cindy is a private, single-user Electron desktop app. One owner is the only user, reviewer and
  product manager. It wraps several coding agents: Claude Code, Codex, Pi and **Hermes**. This row is
  about Hermes only.
- **Hermes** (Nous Research "Hermes Agent", pinned **v0.22.5**) runs as a CLI. Cindy has its own isolated
  Hermes home (`~/.hermes-cindy`).
- **How a turn runs:** each chat turn spawns one `hermes chat --format stream-json --query-file - --in <cwd>`
  child process. Later turns add `--resume <hermes-session-id>`. The child streams JSONL events back:
  text deltas, `tool-use`, `tool-result` and a final `result`. Hermes runs its tools **inside its own
  process**.
- **Access levels:** Cindy's "Full access" maps to `--yolo`. "Default permissions" and "Ask" map to
  `--safe-mode`. Hermes keeps `--yolo` and `--safe-mode` sessions apart, so changing the access level
  mid-chat starts a fresh Hermes session, and the chat loses its history (Cindy shows a notice).
- **Cindy cannot approve or deny single Hermes tool calls.** In v1 the Hermes adapter never receives
  approval requests. Cindy only *observes* `tool-use` events in the stream. It is not known whether
  that event arrives before or after the tool has already run.
- **Cindy's own tools reach Hermes as MCP servers**, through a bridge Cindy controls: `cindy_orca`
  (teams and workers, e.g. `start_team`, `create_worker`), `cindy_experts`, `cindy_docs` and
  `orca_worker_bridge`. Cindy *can* refuse calls in its own bridge, per session.

## 3. What we learned (probe, 2026-11-03)

**Owner's first pick:** a built-in "Options first" toggle per session, shown in the session header.
While it is on, Cindy blocks write and run tools until the owner picks an option, enforced in code
rather than by the model.

The only code-level lock Hermes offers per run is `hermes chat -t/--toolsets <list>`. I tested it in a
throwaway Hermes home against a local stub model server (OpenAI-compatible, logging the `tools` array
and messages of every request) plus a stub MCP server. The probe used no real model, cost nothing,
and did not touch the owner's Hermes homes.

| # | Test | Result |
|---|---|---|
| 1 | Resume an existing session with a different `-t` | **Refused**, exit 2: "Resume retains gateway session policy; creation overrides are unsupported on resume. -t/--toolsets differs from this session's launch: resume without it, or start a new session to use it." |
| 2 | New session, `--yolo -t web` | Only `web_search`, `web_extract` and the lazy meta-tools `tool_search` / `tool_call` / `tool_describe` were exposed. |
| 3 | Same session: model calls `tool_call {calls:[write_file, terminal]}` | **Refused** ("not available in this execution context"); no file created. Control run without `-t`: reachable. So `-t` does lock. |
| 4 | Same session: `tool_search` | Still listed the stub MCP server as an available source. **MCP servers are not scoped by `-t`.** |
| 5 | Tool-level `-t` (`read_file,search_files`, `file:read_file`, `web,probe:probe_tool`) | `invalid_params`. Only whole toolsets are accepted. |
| 6 | Toolset contents | `file` bundles `read_file` + `search_files` with `write_file` + `patch`. **There is no read-only file toolset.** |
| 7 | `--safe-mode -t web` | No tools exposed at all. |

**What this means:**
- **A per-turn lock inside an existing chat is impossible on Hermes 0.22.5.** Toolsets are fixed when the
  session is created. Locking one turn means a fresh Hermes session, which loses the history, just like
  changing the access level does.
- **A session created locked stays locked**, and Hermes itself enforces the lock, so that part is solid.
- **Cindy's MCP tools stay callable** in a locked session. Cindy's bridge must refuse them itself
  (e.g. `start_team` would start real work).
- **A locked session can't read project files**, because there is no read-only file toolset. Suggestions
  would come from the chat and the web only, unless Cindy supplies a read-only reader (see Option D).

## 4. Constraints any design must meet (from the repo's AGENTS.md)

1. **Do not edit existing agents' system prompts.** New prompt text for a *new* feature is allowed.
2. **Fail closed on safety, fail open on convenience.** A safety feature that can silently leak is
   worse than none, because the owner will trust it.
3. **No hidden state.** Anything that changes what the agent can do must be visible in the session header
   and reproducible from files.
4. **Keep the hot path boring.** Changes to the chat loop (`hermes-run.ts` → event translator →
   renderer) need a live proof and a before/after transcript.
5. **Local-first.** No new outbound calls, no credentials on disk, no deleting upstream code.
6. **Do not change the Claude Code, Codex or Pi adapters**, unless a ROADMAP row says so. This row is
   Hermes-only.
7. **Done means proven:** the row closes only at `live-proven`, meaning the owner runs the acceptance
   test in the real app.

## 5. Options now on the table

Estimates are for the implementing agent, tests included, before the owner's live run.

### A. Options-first chat (locked at creation): recommended by me
- **What:** "New chat → Options first". Cindy launches Hermes with read-only toolsets (e.g. `web`,
  `session_search`, `clarify`; no `file`, `terminal`, `code_execution`, `browser`, `delegation`,
  `cronjob`, `computer_use`, `skills`). Cindy's bridge refuses its own acting tools for that session.
  The header shows "Options first". When the owner picks, Cindy opens a full-access chat that carries
  the options conversation as its opening context.
- **Pros:** Hermes enforces the lock, so it fails closed. It's visible, and the hot path isn't touched
  for normal chats.
- **Cons:** the agent can't read project files while suggesting. "Pick" means switching chats, and
  the new chat gets the history as a pasted preamble rather than a native resume.
- **Effort:** about 1–1.5 days.

### B. Watch-and-stop (per turn, current chat)
- **What:** toggle on a turn; Cindy watches the stream and interrupts the turn at the first `tool-use`
  that writes or runs.
- **Pros:** it works in the current chat, with no history loss and no chat switch.
- **Cons:** **not fail-closed.** It's unknown whether `tool-use` arrives before the tool runs, and the
  first write may land before the stop. It also needs a list of which tool names count as writing,
  and that list has to be kept up to date. It touches the hot path.
- **Effort:** about half a day.

### C. Instruction only
- **What:** a visible "Options first" badge. Cindy adds a new rule to the turn's text, e.g. "list
  options, then stop; do not write or run anything".
- **Pros:** cheapest, keeps history, and doesn't edit existing prompts.
- **Cons:** nothing enforces it, and the model can still ignore it, which is what happened in the
  incident.
- **Effort:** about 2 hours.

### D. A plus a read-only reader (fixes A's main cost)
- **What:** Option A, plus Cindy exposes a read-only MCP tool through its own bridge (e.g.
  `read_project_file`, `search_project`, limited to the chat's folder). MCP is not scoped by `-t`, so
  the locked session still sees it, and Cindy controls exactly what it can do.
- **Pros:** a hard lock that can still look at the project.
- **Cons:** a new tool to build and secure (path escapes, size limits). It's bigger.
- **Effort:** about 2 days.

### E. Sidecar options turn (keeps the main chat)
- **What:** with the toggle on, Cindy runs *that one turn* in a separate, locked Hermes session, seeded
  with the main chat's history as a preamble. The options it produces are shown in the main chat. The
  owner's pick then resumes the **original** full-access session, with the options text injected so it
  knows what was offered.
- **Pros:** a hard lock per turn, and the main session's native history is kept.
- **Cons:** the most complex option: two sessions per options turn, history copied as text (token cost
  on long chats), and the hot path is touched. It also has to keep the sidecar out of the chat list.
- **Effort:** about 2–3 days.

### Dropped
- **Lower access level:** `--safe-mode` does not reliably block writes: the default safe-mode session
  still listed `write_file`, `patch` and `terminal`. Switching mid-chat also loses history.
- **Hermes home rule:** text-only like C, but hidden (applies to every Hermes session and isn't shown
  in the header), so it breaks the no-hidden-state rule.

---

## 6. My recommendation

**A now, with D as the follow-up if suggestions without file access turn out too weak.** A is the
smallest option that fails closed, and it meets every constraint in §4. C could ship alongside it as a
cheap soft layer for normal chats, as long as the UI never calls it a lock.

---

## 7. Questions for the reviewer

1. Is a hard, fail-closed lock worth a chat switch (A, D), or is keeping one chat worth more (B, E)?
2. Is E's sidecar approach sound, or is the history copying too fragile?
3. Is there a Hermes 0.22.5 mechanism I missed for gating tools per turn? Known so far: `-t` only at
   creation, `--safe-mode`/`--yolo` only, and no approval callback reaching Cindy.
4. For A/D: which built-in toolsets are safe to leave on? `memory` and `todo` write only Hermes's
   own state, and `web` and `browser` can submit forms.
5. Should an Options-first chat stay locked for its whole life, or offer a "Go ahead" button that
   switches to a full-access chat?

## 8. Unknowns that could change the answer

- Does Hermes emit `tool-use` before a tool runs, or after? (Decides whether B can ever be safe.)
- Does `-t` stop `delegate_task` subagents? (Not tested; excluded anyway in A.)
- Will a later Hermes version allow toolset changes on resume? (Would make a true per-turn lock possible.)
