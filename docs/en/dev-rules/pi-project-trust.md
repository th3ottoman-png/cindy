# Cindy-Managed Pi Project Trust Contract (#2013)

This document defines the input/output contract that PR4 (#2014) can consume; this Issue does not change Pi runtime behavior.

## Source of truth and lifecycle

- trust inputs may only come from Cindy's existing, auditable project approvals. `origin/main` does not yet provide a general project approval store, so the implementation must inject `PiProjectApprovalSnapshot` via the host (宿主); `permissionMode`, tool approvals, MCP approval, plugin enablement state, or Pi user settings must not be interpreted as project trust.
- approvals are re-evaluated on creation, restart, fork, or switching to a new `workingDir`; a running Pi process uses the snapshot taken at startup. Revocation or invalidation takes effect on the next new session; hot unloading of already-loaded resources is not claimed.
- `workingDir` and the git repo root must first be `realpath`'d/normalized, and the host must at the same time provide a trusted `platform` (`posix` / `win32`); guessing from the path string or defaulting to POSIX is not allowed. POSIX canonical bytes may only be marked `utf8-lossless` when they round-trip UTF-8 losslessly; Windows canonical paths may only be marked `utf16-lossless` when they round-trip the host Unicode string losslessly. When the encoding marker mismatches the platform, contains replacement characters, or losslessness cannot be proven, it must be marked `unavailable`, and lossy strings must not be used to generate approval keys. Parse failure, directory disappearance, repo boundary change, or symlink target change all fail closed. The default scope is `repo-root + workingDir`; only when an approval explicitly declares `repo-root` may multiple workingDirs of the same repository share the approval. `extraDirs`, referenced directories, and other workspace roots do not inherit.
- The current pure function only performs comparison-key normalization of separators, extended-length prefixes, and casing on ASCII Windows canonical paths when the host explicitly provides `windowsCaseComparison: ordinal-insensitive`; if the host reports `case-sensitive`, the comparison key's casing is preserved; when absent, `unavailable`, or comparison semantics cannot be proven, it uniformly fails closed. Comparison-key normalization must not overwrite the host-provided canonical I/O path, and eligible output must preserve the extended-length prefix and trailing spaces/dots. Under `ordinal-insensitive`, non-ASCII Windows paths, because JavaScript Unicode folding is not equivalent to Win32 ordinal comparison, must also fail closed as `unavailable`, until the host provides an independent Win32 comparison identity.
- `projectKey` is `${canonicalRepoRoot}\0${canonicalWorkingDir}`; the Windows comparison identity decides whether to fold casing, and separators are always normalized. The approval's `scopeKey` is the canonical root for `repo-root`, and the same composite key for `working-dir`.

## Statuses and resource boundaries

The statuses output by the pure function are only `approved`, `unapproved`, `revoked`, `stale`, `unavailable`. File existence or a scanner hit can only form a resource `discovered`, and cannot claim Pi `loaded`; `loaded` can only be proven by #2011's `get_commands` runtime manifest.

Approval decisions only produce candidate inputs for PR4:

- `skills`: only when the caller explicitly proves `explicitSkills: true`, and in the newly added `canonicalSkillEvidence` provides exact `discoveredPath`/`canonicalPath`-paired 1:1 realpath evidence for each discovered path and verifies the canonical path lies within the approved repo root, may skill directories containing `SKILL.md` be handed to PR4 for assembly; single-file Markdown is not part of the current Cindy project discovery contract and stays `discovered`. The old `canonicalSkills` string array is retained only for compatibility and cannot by itself constitute eligibility evidence. The host must first exclude user, `extraDirs`, referenced directories, and other workspace roots from `discovered.skills`; canonical evidence cannot replace this provenance filtering. When evidence is missing, pairing is inconsistent, symlink targets are outside the repo, or paths are non-canonical, stay `discovered`. Eligible output preserves the canonical I/O path and does not substitute the comparison key; PR4 must fully materialize eligible directories into the per-session-isolated `configHome`, handing only the snapshot path to Pi; any copy or re-verification failure fails closed the whole group. The capability bit only takes effect with a strict boolean `true`; absent or other truthy values are all false. It does not represent that Pi has already `loaded` these resources;
- `settings`: assemblable only when projected through the field allowlist (outputting `settingsProjection.values`), with 1:1 realpath evidence with exact `discoveredPath`/`canonicalPath` pairing provided for each discovered path and the canonical path verified to lie within the approved repo root, and with packages/extensions simultaneously proven off; `settingsProjection.sourcePath` must be the original lexical path from `discovered.settings`, and only after success is the output rewritten to the corresponding canonical I/O path. Missing evidence, inconsistent pairing, out-of-repo symlink targets, or non-canonical paths stay `discovered`. This contract does not allow raw `.pi/settings.json` by default. The current allowlist only allows pinned Pi v0.83.0's `compaction.reserveTokens` / `compaction.keepRecentTokens` as non-negative safe integers; unknown fields, future newly added fields, `defaultProjectTrust`, provider/auth, path, and resource-loading configuration all fail closed. The output is a deep-cloned, frozen startup snapshot; `eligibleSettingsPaths` is a compatibility-only field containing the canonical `sourcePath` used by the projection, and the discovered raw settings path must not be treated as an assemblable input; an empty projection stays `discovered`.
- `packages` / `extensions`: always `discovered` or `blocked`; must not be installed, loaded, or executed.

## Launch and isolation invariants

- Do not pass `--approve`, do not write the user's `~/.pi/agent/trust.json`, do not set `defaultProjectTrust=always`; assembling trust.json, `defaultProjectTrust`, or equivalent configuration belongs to #2014.
- Do not write or reuse the entire user `~/.pi/agent`, and do not inherit auth/provider/settings/trust/credentials. Per-session `PI_CODING_AGENT_DIR` isolation, temp directories, and concurrent session input isolation remain unchanged.
- `launch` output is fixed to `approve:false`, `writeTrustJson:false`, `inheritUserPiHome:false`, `allowPackages:false`, `allowExtensions:false`. The pure function reads no configuration, writes no files, and does not launch Pi.
- If Pi cannot simultaneously "trust skills/settings while blocking packages/extensions", #2014 must narrow to explicit skills-only, or block project settings; bypassing with `--approve` is not allowed.

## Comparison with existing boundaries

- #1729: only Cindy-approved project mappings are allowed; unconditional `--approve`, reuse of the entire user Pi directory, and default-open packages/extensions are forbidden.
- #1705: the execution and presentation contract for packages/extensions under non-TUI hosts remains unresolved; this contract does not reopen that scope.
- #1967: isolated `PI_CODING_AGENT_DIR` is an intentional concurrency/credential boundary; this contract does not circumvent isolation by copying or linking the user Pi home.
- #2030: Pi v0.83.0 `get_commands` fixtures serve as the resource-discovery fact baseline; after #2053/#2011's manifest types land, only field wiring needs re-checking; do not copy their unmerged types.
